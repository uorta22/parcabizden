Başkan Kararı

Konseyin Anlaştığı Noktalar

In-memory rate limit production'da çalışmıyor. 3/5 danışman bağımsız olarak aynı noktaya ulaştı. Vercel serverless'ta her request farklı instance'da çalışabilir; Map() tabanlı rate limit sıfırlanır. Bu "kötü tasarım" değil — işlevsiz kod. Sahte güvenlik algısı oluşturur.
Admin kontrol yüzeyi riskli. Contrarian, Outsider, First Principles üçü de işaret etti. Anlaşmazlık "ne kadar riskli" üzerinde; "risk var mı" üzerinde konsensüs var.
JWT localStorage'da XSS'e açık. Birden fazla danışman işaret etti. "Kötü pratik" kategorisinde konsensüs var, MVP'yi engellemez ama bilinçli karar olmalı.

Konseyin Ayrıştığı Noktalar

Admin guard UI tercihi mi, güvenlik açığı mı?

  • Contrarian + Outsider: Production blocker. Client-side admin guard = güvenlik yok.
  • First Principles + Executor: Asıl soru requireAdmin() fonksiyonunun tüm PHP endpoint'lerinde çağrılıp çağrılmadığı. Backend korumalıysa frontend guard sadece UX katmanıdır.
Gerçek cevap: İkisi de haklı, farklı şeyleri konuşuyorlar. Frontend'deki admin kontrolü zaten korunmaması gereken şey. Asıl mesele PHP API'nin Authorization header'ı doğrulamadan işlem yapıp yapmadığı — ve bu henüz doğrulanmadı.

Peer Review'ın Yakaladığı Kör Noktalar

PHP backend deployment pipeline hiç sorgulanmadı. Bu konseyin en büyük başarısızlığı. Natro'ya git push ile auto-deploy yapılıyor — ama:
  • display_errors production'da açık mı? (Türkiye shared hosting'lerde sıkça açık gelir)
  • DB credentials config.php içinde mi, .env'de mi? .env web root dışında mı?
  • PHP dosyaları public_html altında mı? vendor/ web'den erişilebilir mi?
  • Migration'lar otomatik mı? Zero-downtime yok — deploy sırasında yarım kalan request'ler ne olur?

Eğer config.php web root içindeyse ve display_errors = On ise, diğer tüm güvenlik katmanlarının önemi kalmaz.
requireAdmin() coverage audit yapılmadı. Fonksiyonun var olması yeterli değil. Tüm admin endpoint'lerinde gerçekten çağrılıp çağrılmadığı grep ile doğrulanmadı.

Öneri Özeti

ParcaBizden şu haliyle tam production-ready değil — ama 2-3 somut fix ile MVP seviyesine çıkabilir. Bu platform bir Türkiye pazarı MVP'si, Fortune 500 uygulaması değil. Çökmemesi ve kullanıcı verisini ifşa etmemesi gerekiyor.

🧠 5 Danışman Tam Yanıtları ▼
🔴 Contrarian
Sert Eleştiri

Bu sistemin en kritik güvenlik açığı şu: admin yetkisi client-side'da kontrol ediliyor. user.is_admin frontend'de set ediliyorsa, herhangi biri localStorage'ı editleyerek admin paneline erişebilir. Eğer PHP backend her endpoint'te token'ı parse edip is_admin claim'ini doğrulamıyorsa, admin API'larının tamamı açık demektir. Bu production blocker'dır.

Elle yazılmış HS256 implementasyonu ikinci kritik sorun. JWT kütüphaneleri yıllar içinde timing attack, algorithm confusion ("alg": "none" bypass), key confusion gibi onlarca CVE'den geçti. /tmp tabanlı rate limiting paylaşımlı hosting ortamında anlamsız. In-memory Map ile Next.js rate limiting Vercel'de çalışmaz. email_verified = 1 hardcoded. Sepet localStorage'da cross-device yok. Güvenlik katmanlarının çoğu gerçek değil, dekoratif. Saldırı yüzeyi düşündüğünden çok daha geniş.

🔵 First Principles
Temel Analiz

"Production-ready mı?" sorusu, production'ın ne anlama geldiğini tanımlamadan anlamsız. Asıl soru: Bu sistemin başarısızlık modu nedir ve o başarısızlık kabul edilebilir mi?

Admin paneli client-side guard ile korunuyor — bu bir güvenlik mekanizması değil, bir UI tercihi. Backend'de is_admin kontrolü yoksa, URL'yi bilen herhangi biri admin işlemlerini doğrudan API'ye atarak yapabilir. Bu mimari düşük hacimli MVP için kabul edilebilir risk profili taşıyabilir — ama bu bilinçli bir karar olmalı, varsayım değil. Asıl soru: Admin API endpoint'leri server-side'da korumalı mı?

⚠️ Expansionist
Off-topic: Soruyu yanıtlamadı

Not: Bu yanıt güvenlik audit sorusunu değil, pazar fırsatlarını ele aldı. 5/5 peer reviewer bunu kör nokta olarak işaretledi.

Bu projenin gerçek riski "production-ready değil" değil — "çok küçük düşünülmüş". Türkiye'de 15 milyon araç var. Parça pazarı 80+ milyar TL. Multi-part request flow fırsatı var. Admin zayıflığını tedarikçi paneline dönüştür — gerçek RBAC gelir. Rate limit datası trend analizi için değerli: hangi parça nerede aranıyor? En büyük eksik: tedarikçi tarafı yok. Platform tek taraflı. İki taraflı marketplace'e geçiş, mevcut altyapının 3x değerinde.

🟣 Outsider
Dış Bakış

Hayır, production-ready değil. Admin panel koruması tamamen çökmüş. Frontend'de user.is_admin kontrolü yapmak, kapıya "yetkisizler giremez" yazan kağıt yapıştırmak gibi. JWT'yi localStorage'da saklamak XSS'e açık kapı bırakır — HttpOnly cookie olmalıydı. KVKK uyumu da bu yüzden sorun.

Rate limiting'in in-memory Map ile yapılması Vercel'de işe yaramaz. Sosyal medya bağlantıları boş string — GSC doğrulama pasif. Sepet localStorage'da, kullanıcı sekmeyi kapatırsa sepet gitti. WhatsApp ve iletişim bilgileri hardcoded, .env üzerinden yönetilmeli.

🟠 Executor
★ 5/5 reviewer tarafından en güçlü seçildi

Gerçek sorun şu: "Production-ready" sorusu yanlış çerçevelenmiş. Doğru soru: "Hangi şeyler canlıda bozuk, hangileri sadece kötü?"

Gerçekten bozuk: (1) In-memory rate limit — Vercel'de her invocation'da sıfırlanır, şu an hiç rate limiting yok. (2) /tmp @mkdir hata sessizce yutulur, rate limit devre dışı kalabilir.

Sağlam: hash_equals var (timing attack önlendi), PDO parametreli.

Aksiyon: Chat rate limit → Redis/Vercel KV (2 saat iş). Sosyal medya ya doldur ya kaldır (10 dk). @mkdir suppress'i kaldır. requireAdmin() tüm endpoint'lerde kullanılıyor mu kontrol et.

En Büyük Kör Nokta: Expansionist

Pazar büyüklüğü gerçek ama sorulan soru "production-ready mi?" — Expansionist bunu cevaplamadı. "Fırsat kaçırılıyor" demek, mevcut sistemin güvenli çalıştığını söylemez. Strateji tartışması teknik audit ile karıştırıldı. Konsey için ders: Expansionist'e soru daha spesifik verilmeli — "bu sistem güvenli mi ölçeklenir mi?"

5 Reviewer'ın Ortak Yakaladığı Kör Nokta #1

PHP backend deployment pipeline. Natro'ya git push ile auto-deploy oluyor ama: display_errors durumu, config.php'nin web root konumu, vendor/ erişimi, migration sıralaması — hiçbiri doğrulanmadı. Bu, tüm diğer güvenlik tartışmalarının temelini etkiliyor.

5 Reviewer'ın Ortak Yakaladığı Kör Nokta #2

requireAdmin() fonksiyonunun tüm admin endpoint'lerinde gerçekten çağrılıp çağrılmadığı grep ile doğrulanmadı. "Var" ile "her yerde kullanılıyor" farklı şeyler. Tek bir grep -rn "requireAdmin" api/ bu belirsizliği giderir.

💻 Doğrulama Komutları ▼

Bu komutlarla konseyin cevaplayamadığı soruları kendin doğrulayabilirsin:

requireAdmin() coverage

# Admin endpoint'leri listele
grep -rn "requireAdmin\|is_admin" php-backend/api/

# Admin function olmayan php dosyaları bul (admin/ klasöründe)
grep -rL "requireAdmin" php-backend/api/admin/

PHP display_errors durumu

# config.php içinde display_errors kontrolü
grep -n "display_errors\|error_reporting\|APP_ENV" php-backend/api/config.php

Next.js in-memory rate limit

# Rate limit Map kullanımını bul
grep -rn "new Map\|rateLimit\|rateLimitMap" src/

# Vercel KV / Upstash kullanımı var mı?
grep -rn "kv\|upstash\|redis" src/ package.json

# Boş href bul
grep -rn 'href=""' src/
